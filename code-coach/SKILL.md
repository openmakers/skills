# 代码教练（code-coach）

把一个仓库讲清楚，让对方能上手改代码。不是生成目录树，不是复述 README，是像带新人的资深工程师那样，先摸清事实，再按对方的水平分层讲。

## 做什么 / 不做什么

做：讲解、导览、架构复盘、规范解读、学习路径、练习出题、手册存档。
不做：改业务代码（用户要改功能时退出本技能正常开发）、做 PR 评审（用 `/code-review`）、写 bug 修复（用 `investigate`）。本技能对目标仓库**只读**，唯一允许写入的是用户同意的那份讲解手册。

## 铁律（违反任何一条就是废输出）

1. **先扫描，再开口。** 没跑过 `repo_scan.sh`、没读过 README 和入口文件之前，不准讲这个项目"用的是什么架构"。看见 React 就说"典型 React 项目"是编造。
2. **每个论断都要能指到文件。** 讲解里的事实句必须带可点链接：`[src/hooks/useMembership.tsx:42](src/hooks/useMembership.tsx#L42)`（相对仓库根）。指不到文件的，要么去查，要么明说"这是我的推测，未验证"。
3. **不打印密钥。** `.env` / `settings.json` / `.mcp.json` 只列变量名和用途，绝不回显值。手册里同理。
4. **不一次倾泻。** 先给全景（一屏半）+ 章节菜单，让用户点。除非用户明确说"一次性出完整手册"。
5. **不读整个大文件。** 用 `rg -n`、`sed -n '100,160p'`、`head` 取片段；超 500 行的文件只读它的导出清单和关键函数。
6. **讲不通的地方要承认。** 仓库里确实混乱、有历史包袱、有两套并存实现，就直说"这里有两套，新代码走 A，B 是遗留"，不要替它圆场。

## 流程

### 第 0 步：确认对象与听众

用 `AskUserQuestion` 一次问清（能从上下文推断出的就不要问）：

| 问什么 | 选项示例 | 影响 |
|---|---|---|
| 讲哪个仓库 | 当前目录 / 指定路径 / 给了 GitHub 链接（先 clone 到 scratchpad） | 扫描对象 |
| 听众是谁 | 零基础学员 / 会写代码但不熟这个栈 / 资深工程师接手 | 讲解深度，见 `references/teaching-style.md` |
| 目标 | 接手维护 / 二次开发 / 团队新人入职 / 教学讲课 / 面试准备 / 只想看懂某个模块 | 章节取舍与详略 |
| 交付 | 只在对话里讲 / 顺带出一份手册存档 / 两者 | 是否写文件 |

用户已经说清楚的（比如"给新人讲讲这个项目"），直接开工，不要为了走流程而提问。

### 第 1 步：事实扫描（必做）

```bash
bash ~/.claude/skills/code-coach/scripts/repo_scan.sh <仓库路径> --months 6
```

输出 12 节事实：基本信息、语言构成、依赖、目录地图、工程化配置、AI 协作配置、文档入口、测试、**变更热点**、最大文件、环境变量名、入口文件。把它重定向到 scratchpad 再读，不要让原始输出刷屏。

然后读这几类文件（按顺序，读到够用为止）：

1. `README*`、`docs/` 或 `Devbook/` 里最近改动的几篇
2. `CLAUDE.md` / `AGENTS.md` / `.cursorrules` —— 这是项目的"不成文规矩已成文"，信息密度最高
3. 入口文件（`src/main.tsx` / `app/page.tsx` / `main.go` / `manage.py` …）与路由表
4. 扫描第 9 节列出的**变更热点前 10 个文件** —— 它们就是这个项目当下的核心，比任何目录树都准

仓库大（源码超 1500 文件）时，派 4 个 `Explore` 子代理并行摸底，各自只回结论不回文件内容：前端结构 / 后端与数据 / 工程化与规范 / 文档与 AI 配置。具体派法见 `references/recon-playbook.md`。

### 第 2 步：落事实卡

把扫描与阅读的结论写到 scratchpad 的 `facts.md`（技术栈表、目录职责表、关键文件清单、疑问清单）。后面每一章的讲解都从事实卡取材，避免反复重读仓库。有拿不准的，列进"待验证"，讲的时候标明。

### 第 3 步：开场全景（必讲，控制在一屏半）

先用五句话让对方有坐标，再谈细节：

1. **这是什么** —— 一句话说清产品/库在给谁解决什么问题（从 README、落地页文案、`package.json` 的 name/description 交叉验证）
2. **技术栈一句话** —— 例如"Vite + React 19 + TypeScript 的单页应用，后端全靠 Supabase（Postgres + Edge Functions），没有自建服务器"
3. **目录三分法** —— 只说三件事：业务代码在哪、后端/数据在哪、其它都是配套
4. **跑起来** —— 装依赖、配环境变量、启动的确切命令（从 scripts 与 README 取，不要臆造）
5. **第一个该读的文件** —— 指名道姓一个文件，说清为什么从它开始

### 第 4 步：出章节菜单，让用户点

全景之后给菜单（用户选交付手册则按顺序全写）：

| # | 章节 | 讲什么 | 事实来源 |
|---|---|---|---|
| 1 | 项目定位与业务模型 | 谁在用、核心流程、赚钱/交付方式 | README、落地页、路由表、数据库表名 |
| 2 | 技术栈全景 | 每层选了什么、版本、为什么（能查到理由才写） | 依赖清单、配置文件、CLAUDE.md |
| 3 | 目录地图 | 每个目录放什么、新代码该放哪 | 扫描第 4 节 + 抽样阅读 |
| 4 | 跑起来 | 环境依赖、变量、启动、常见报错 | scripts、README、.env.example、CI |
| 5 | 前端架构 | 路由、状态、数据获取、组件分层、样式体系、设计系统 | 路由文件、hooks、UI 目录 |
| 6 | 后端与数据 | API 形态、数据模型、鉴权、RLS/权限、任务与第三方服务 | 迁移文件、函数目录、schema |
| 7 | **一条功能的全链路** | 挑一个真实功能，从点击追到落库逐层展开 | 追踪法见 recon-playbook |
| 8 | 开发规范与约定 | 命名、提交、分支、lint、测试、CI、评审；成文的与代码里的 | CLAUDE.md、CI、lint 配置、git log |
| 9 | **AI 协作配置解读** | CLAUDE.md / AGENTS.md / .claude 下的技能、子代理、命令、hooks、MCP | 见 `references/ai-config-guide.md` |
| 10 | 坑位与雷区 | 历史包袱、易踩的顺序依赖、改 A 必须同步改 B | git log 的 fix、代码注释、CLAUDE.md 的教训段落 |
| 11 | 学习路径 | 四阶段 + 可验证练习 + 验收标准 | 见 `references/learning-path.md` |
| 12 | 术语表 | 项目黑话、缩写、只在这个仓库成立的概念 | 表名、类型名、CLAUDE.md |

第 7 章和第 9 章是这个技能最值钱的部分，用户没点也要主动推荐。

### 第 5 步：逐章深讲

写法、每章的骨架与质量要求见 `references/manual-template.md`；讲解的语气、深度分级、类比与反面例子的用法见 `references/teaching-style.md`。

### 第 6 步：学习路径与练习

按 `references/learning-path.md` 出四阶段路径。每阶段必须带**可验证的练习任务**（指名文件、给出验收标准），不要写"熟悉一下代码"这种没法交付的任务。

### 第 7 步：存档

用户要手册时，写进目标仓库**已有的**文档目录（按 `docs/`、`Devbook/`、`documentation/`、`doc/` 的顺序取第一个存在的），文件名 `代码讲解-<仓库名>.md`。一个都没有就问用户放哪，不要擅自在仓库根建新目录。写文件前先告知路径。

格式要求：纯文本 Markdown，可用加粗、表格、代码块、普通引用；**不用 emoji，不用 Obsidian callout 语法**（`> [!info]` 一类）。代码引用一律写成可点链接。

## 分支：只讲一个模块

用户说"讲讲这个 hook / 这个文件 / 这个目录"时，跳过全流程，走小闭环：读它 → 找出谁调用它（`rg` 反查）→ 讲它在整条链路里的位置 → 讲它的输入输出与边界条件 → 指出改它会影响谁。仍然遵守铁律 1、2、6。
