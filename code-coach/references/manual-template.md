# 《代码讲解手册》十二章骨架与质量标准

每章都按"这一章要回答的问题 → 骨架 → 质量标准"来写。骨架里的方括号是占位，必须用真实事实替换，替换不了就删掉该块，不要留空话。

通用格式要求：纯文本 Markdown；不用 emoji；不用 Obsidian callout（`> [!info]` 一类），需要提示就用加粗小标题领起的普通段落；代码引用写成可点链接 `[src/a/b.ts:42](src/a/b.ts#L42)`；每章开头一句话说清"读完这章你能做什么"。

---

## 第 1 章 项目定位与业务模型

回答：这东西给谁用、解决什么问题、怎么产生价值。

骨架：一句话定位 → 主要用户角色（2-4 个，每个角色的核心动作）→ 核心业务流程（一条主干，3-6 步）→ 业务上的关键名词（后面会在表名和类型名里反复出现）。

质量标准：一个不懂这个行业的工程师读完能复述业务；名词与代码里的表名/类型名对得上（对不上要指出）。

## 第 2 章 技术栈全景

回答：每一层选了什么，版本多少，为什么。

骨架：一张表（层 / 技术与版本 / 在仓库哪里体现 / 备注），层次按：语言与运行时、构建工具、前端框架与 UI、状态与数据获取、后端形态、数据库、鉴权、存储、第三方服务、部署与 CI。表后写 2-3 段"值得注意的选型"：不寻常的选择、已被官方废弃的依赖、版本明显落后的依赖。

质量标准：版本号来自锁文件或 manifest，不是记忆；"为什么这么选"只写能在 README/CLAUDE.md/提交信息里找到依据的，找不到就写"未见记载"。

## 第 3 章 目录地图

回答：哪个目录放什么，我写新代码该放哪。

骨架：顶层目录表（路径 / 职责 / 文件数 / 要不要看）→ 主源码目录的二级展开 → "新增一个页面/接口/组件分别该放哪"的落位指南 → 不用看的目录（产物、备份、临时）明确列出来。

质量标准：职责描述来自抽样阅读而非目录名猜测；落位指南要指出现有的命名与放置惯例（看 3 个同类文件归纳出来）。

## 第 4 章 跑起来

回答：从零到本地能访问，要做哪些事。

骨架：前置依赖与版本（Node/Python/包管理器）→ 安装命令 → 环境变量表（变量名 / 用途 / 从哪申请 / 是否必需，**绝不写值**）→ 启动命令 → 验证成功的标志 → 常见报错与处理（从 README、CI 配置、提交历史里的 fix 归纳）。

质量标准：命令逐条来自 `package.json`/Makefile/README，不臆造；能跑的就亲自跑一次装依赖或 lint 验证命令有效（不要跑会改数据的命令）。

## 第 5 章 前端架构

回答：一个页面是怎么被组装、拿到数据、渲染出来的。

骨架：路由表（路径 / 页面组件 / 是否需要登录 / 备注）→ 全局 Provider 链（`App` 里包的每一层分别管什么）→ 状态分层（服务端状态 / 全局 UI 状态 / 组件本地状态各用什么方案）→ 数据获取的标准写法（贴一段真实代码并逐行说明）→ 组件分层与复用约定 → 样式体系与设计 token → 表单、弹窗、通知等横向能力的统一入口。

质量标准：每一条都指到真实文件；"标准写法"必须是仓库里出现三次以上的写法，不是你认为好的写法。

## 第 6 章 后端与数据

回答：数据存在哪、谁能读写、业务逻辑在哪一层。

骨架：后端形态（自建服务 / serverless / BaaS，一句话）→ 数据模型（核心表 8-15 张：表名 / 作用 / 关键字段 / 关联）→ 权限模型（鉴权怎么做、授权在哪一层、RLS 或中间件的规则要点）→ 业务逻辑分布（前端 / 服务端函数 / 数据库函数与触发器各承担什么，**触发器一定要单独点名**，新人最容易忽略）→ 外部服务清单 → 迁移与上线流程。

质量标准：表结构来自迁移文件或 schema，不是推测；写明哪些逻辑藏在数据库里（触发器、RPC、默认值、约束），因为这些读代码看不见。

## 第 7 章 一条功能的全链路（重点章）

回答：点一下按钮，到底发生了什么。

骨架：选题说明（为什么挑这个功能）→ 分层链路表（步骤 / 文件链接 / 这一层干了什么 / 关键参数）→ 每层贴 5-15 行真实代码并解释 → 数据落到哪几张表 → 失败路径（超时、无权限、余额不足等分别在哪一层被拦）→ **"要在这条链路加一个字段，依次要改这 N 处"**。

质量标准：链路是真的追出来的，每一跳都有文件依据；最后那段改动清单能直接当任务单用。

## 第 8 章 开发规范与约定

回答：在这个仓库里，怎么写才算"合群"。

骨架：成文规范（来自 CLAUDE.md / CONTRIBUTING / lint 配置，逐条翻译成人话）→ 不成文约定（从代码归纳：命名风格、文件组织、错误处理套路、注释习惯）→ 提交与分支（`git log --format=%s -50` 归纳出的真实风格）→ 质量门禁（lint、类型检查、测试、CI 各卡什么，哪些是硬门槛哪些形同虚设）→ 评审与上线流程。

质量标准：区分"文档写了的"和"代码真在做的"，漂移处按 recon-playbook 第 6 节标注出来。

## 第 10 章 坑位与雷区

回答：哪些地方会让新人第一周就翻车。

骨架：按"坑 / 现象 / 原因 / 正确做法"四列成表，6-12 条。素材来源：CLAUDE.md 里带"教训""历史""不要"字样的段落、`git log --grep=fix` 高频主题、代码里的 TODO/FIXME/HACK 注释、同一文件反复被 fix 的位置、跨文件的隐式联动（改 A 必须改 B）。

质量标准：每条都能指到证据（提交哈希或文件行）；不写"注意代码质量"这类废话。

## 第 12 章 术语表

回答：他们说的那个词到底指什么。

骨架：术语 / 含义 / 在代码里的体现 / 容易混淆的近义词。收录标准：只在这个项目成立的概念、业务缩写、与通用含义不同的词（典型如界面上叫 Basic、数据库里却存成另一个值这类名实不符的命名）。

质量标准：每个术语给出至少一个代码位置；特别收录"名不符实"的命名，这是新人误解的主要来源。
